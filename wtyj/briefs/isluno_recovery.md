# ISL-12 — Recovery, reminders and legacy transition

Candidate for issue #354, built on accepted backend 41ded819d2102cf9b3fe284c31118552f231c0f4 and dashboard 1eaed6ce1108b79d473818a9f349a80675ee1636. This is isolated implementation evidence, not release or number activation.

## Runtime behavior

Every verified Isluno inbound turn records its customer/journey/schema scope and unique trigger before processing. A new reply suppresses queued reminders, including a failed understanding turn. Duplicate triggers cannot restore an earlier reminder anchor. The existing single understanding call recognizes semantic reminder opt-out; plain opt-out retains the saved trip; combined guest/document corrections use the normal application result and keep a separate opt-out acknowledgement. Six language copies are present; Papiamento remains pending native review.

The tenant-owned `clients/mermaid/config/isluno_recovery.json` ships **disabled**. A missing or disabled policy schedules nothing. Its optional 6-hour and 18-hour reminders bind the current session revision, itinerary, original response and inbound timestamp. Dispatch requires the original response accepted, unchanged draft journey, no reply/opt-out/takeover/completion, fresh verified automation/account controls, no queued inbound processing and an open service window younger than 24 hours. Both eligibility and guards run again after the durable claim and immediately before real transport. Recipient pacing is shared with existing discovery. After downtime, a superseded earlier slot is suppressed rather than sent in a catch-up burst.

Accepted reminders never replay. Exceptions become ambiguous, a crash after claim remains claimed, and neither automatically retries. Rejected/blocked/window-closed outcomes also remain terminal for this reminder. The existing payment, immutable document, partial fulfillment and email-consent ledgers retain their accepted no-replay behavior.

An understanding/validation exception creates an operator incident containing the exception class only. The saved itinerary is retained; the customer receives no fabricated success or delivery claim and the same event cannot recall the model. A successful new turn marks the earlier understanding incident `progress_resumed_new_turn`; this does not assert delivery. Today exposes incidents, reminder states, discovery failures and legacy quarantine in its authenticated projection and attention count. The dashboard offers inspection links, without a blind resend action.

## Cutover and rollback

On future authorized startup with the Isluno feature enabled, lifespan calls transition.ensure before resuming legacy work or accepting webhooks. The same verified fence is checked by the conversation caller. A transaction journals hashes and explicit dispositions for outstanding records in existing Mermaid reservation, checkout-link, reminder, document-job, date-change, email and allowlisted WhatsApp inbound tables. Missing tables are skipped. Original business rows are not rewritten. Checkout links without a status are conservatively quarantined, including historical links whose paid status cannot be established from that row.

Pending work requires operator review with no automatic replay. Sending/claimed/ambiguous or previously attempted work requires uncertain-outcome reconciliation. Legacy checkout GET/POST returns 410; confirmation, payment completion, automated sender, abandoned reminder, document claim/reconciliation, date buttons, language picker and reservation email callers are fenced. Quarantined stale inbound recovery explicitly records `isluno_legacy_quarantine` rather than replaying the turn. Other tenant behavior remains outside the Mermaid fence.

Rollback means restoring prior feature configuration **while retaining the current fence-capable code and database ledgers**. The durable marker keeps legacy automatic actions stopped even with the feature off; queued Isluno reminders become suppressed with reason `rollback`. Reactivation does not revive them. Operator reconciliation and manual follow-up remain required; no automatic unquarantine/re-enable function is provided. Rolling binaries back to code that predates these guards would bypass this guarantee and is not the defined rollback. Historical reads and the existing manual inbox are preserved.

## Independent-review corrections

R1: conversation claims now persist `claimed_at`. Recovery runs before optional reminder-policy dispatch, on actual inbound replay and on authenticated Today reads. An undecided claim older than 15 minutes gets one durable `understanding_stalled` / `stale_claim_outcome_unknown` incident. The age is an attention threshold, not proof that a remote request failed. Recent claims and calls executing in this process are excluded; executing ownership lasts through durable decision recording. After restart, expired unfinished claims become inspectable without another model call. Cross-process liveness is not inferred; the disposition explicitly remains outcome unknown. The transaction rechecks decision/outcome before inserting and does not duplicate a known model-failure incident. Saved-itinerary links bind the claim baseline. A subsequent applied turn marks progress resumed without claiming delivery. Old rows lacking timestamps start observation on first verified scan; other account scopes are neither stamped nor surfaced.

R2: the six opt-out acknowledgements now assert only that reminders stopped. A combined guest/document correction includes the normal application summary rather than claiming details stayed unchanged. Opt-out bypasses the quote-only early return, so acknowledgement survives both newly prepared and replayed quote requests. ### Residual R1: completed-message replay is not new progress

Resolution now reads the current trigger's durable applied outcome and compares its session revision with each affected claim's saved baseline. Trigger inequality alone never resolves an incident. Missing outcomes and older completed outcomes leave the alert open; an applied outcome with a revision greater than the affected baseline may mark resumed progress. The comparison and update run in one transaction under the verified customer scope.

The actual-handler regression exercises both ordinary understanding exceptions and stalled/crashed claims.
