# ISL14 admission/drain coordination — accepted locally, release gated

The new coordinator is inactive by default and uses the existing Mermaid SQLite database. It does not replace inbox/AI-owner controls, add a service, modify provider subscriptions or authorize a release. The absent `/features/mermaid_cutover_coordination` flag is false. No deployed configuration was changed.

## Implemented boundary

`shared/mermaid_maintenance.py` owns additive coordination, worker, accepted-message snapshot and audit tables. `state_registry.wa_claim_inbound_processing` calls its admission guard inside the **same BEGIN IMMEDIATE transaction** as the existing dedup marker and normalized-payload insert. Closing takes that same writer lock and snapshots pre-existing recoverable messages. Therefore a racing new event is either committed before closure and included, or rejected before dedup is consumed. The actual Zernio handler returns503 on that exception; existing accepted duplicates remain200 without a new background task. Non-customer `message.sent`/`message.failed` acceptance semantics are unchanged.

Workers claim durable UUID records before entering participating code. Closure prevents new scheduled/delivery/transport roots. An already-active parent can finish nested work during the bounded drain. Already accepted inbound IDs can enter their original processing path; recovery can reconstruct those durable batches. The final `seal` transaction refuses active or operator-review workers, incomplete snapshotted inbound work, ambiguous/pending send ledgers, incomplete declared producer coverage and unreviewed populated Isluno ledgers. Once sealed, even recovery cannot claim a new worker. A daemon thread disappearing, lease expiring or deadline passing never counts as completion.

An exception leaves an `operator_review` worker with an uncertainty disposition; abrupt process loss leaves its durable `active` record. Both block seal indefinitely pending separately reviewed reconciliation. Returning normally is not enough if a business delivery ledger says sending/uncertain/pending. These ledgers and original customer/business rows are not deleted or advanced by the gate. This candidate deliberately has **no automatic claim retirement, administrative force-ready, or ambiguous-send replay**. A drain deadline failure keeps admission closed and blocks promotion; resolving or cancelling that condition requires a concrete reviewed reconciliation action rather than changing inbox settings or deleting gate rows.

The status endpoint is `GET /isluno/maintenance` on the existing authenticated dashboard router. It returns phase/generation/deadline, bounded claim metadata/dispositions and aggregate pending/unknown-ledger counts; no customer payloads or message IDs. `ready:false` is deliberate: a snapshot is not an atomic seal or execution authorization. Mutating close/seal/reopen functions are not exposed as public HTTP endpoints. They are operator primitives for a separately approved exact action, not commands to execute during preparation.

`isluno_transition.ensure` now checks the current sealed generation, complete declaration, retained-work state and deadline **inside its cutover transaction** when coordination is installed. The proposed activation configuration must bind `/mermaid_maintenance/activation_generation` to the sealed integer. Missing/stale/expired bindings fail closed. Existing cutover markers retain their prior one-way quarantine semantics. Removing the coordination feature flag does not remove an existing durable gate.

## Coverage and explicit exclusions

`maintenance-coverage.json` records the exact29 decorated entry points by function, source line and role. The covered paths are:

- Accepted Zernio/Meta background processing, debounce admission/flush, and stale-inbound recovery. Actual background inbound IDs bind to the closed-generation snapshot; non-customer events bypass the customer wrapper.
- Mermaid abandoned reminders, pending document reconciliation, consented reservation email preparation/transport and both demo-payment completion roots.
- Isluno scheduled recovery, discovery/quote/fulfillment delivery and asynchronous paid-email workers. A newly started email thread cannot inherit permission merely because its parent finished; after closure it is blocked before entry and its durable pending work cannot be counted complete.
- Shared reply dispatch, direct Meta send helpers, the direct HTTP POST functions in the existing Zernio client, typing dispatch, Isluno POST and Mermaid SMTP boundary. Nested claims span actual work, not just queue counters.

Coverage declaration is **not automatic proof of deployed producer inventory**. `close` requires the full named set and an operator evidence reference; this validates the declaration's completeness, not the truth of an arbitrary reference. Before anyone may use it operationally, independently verify the exact participating runtime and quiesce/exclude all old binaries, extra consumers, manual/direct scripts, operator mutation paths, and any generic email-poller/hold-reaper/ali-quote-recovery processes not covered here. Those external participants are explicit `operator_writers`/`runtime_inventory` prerequisites, not silently assumed idle. Current H1–H7 evidence did not inspect them. A process-local flag or an empty local count cannot waive this prerequisite.

The initial use is Mermaid-to-Isluno cutover. Unreviewed populated Isluno ledgers with status/decision/outcome fields block a later seal instead of guessing their business semantics. This conservative stop is intentional; future re-drain after Isluno activity requires explicit ledger-disposition coverage. Historical Mermaid drafts waiting for a customer are retained by the accepted quarantine. Failed/paused members of the accepted closing snapshot and ambiguous send claims block this drain; they require operator-visible reconciliation, never false completion.

## M-R1 / M-R2 integrated corrections

Every member of the closing snapshot is now evaluated through a LEFT JOIN, including an absent inbound row. The only automatically accepted terminal pairs are `replied/provider_send_ok`, explicit ignored-contact/ignored-phone/blocked-conversation/non-text dispositions, and `escalated/human_takeover_ai_muted`, all with empty error/processing-token/lease metadata. Generic `processed`, unknown reasons/statuses, failed delivery, malformed terminal metadata and missing rows block seal and activation. Operator status exposes fixed aggregate disposition categories, never raw unknown values or customer IDs.

The real delivery-failure commit writes `send_failed/provider_send_failed/provider_delivery_unconfirmed` while creating an operator item; the new regression proves this still blocks seal. Notification creation is not reconciliation. Existing recovery sets `superseded/newer_outbound_exists` when any newer assistant/operator thread entry exists (excluding model-status notices). That condition does not causally resolve this particular turn or its uncertain send. An actual recovery regression with an unrelated synthetic operator note therefore retains supersession as a review blocker. Reviewed successful reply and intentional owner/policy dispositions continue to seal normally through the real state-transition API.

`zernio_dm_client.send_dm_reply` itself is now a participating transport boundary, including its default SDK `client.inbox.send_inbox_message` branch. The gate runs before credential lookup/client construction. Draining/sealed roots cannot invoke either; open/default-off/other-tenant behavior and existing provider-account checks are preserved. A nested already-active worker may finish during its original drain deadline. Caught SDK exceptions retain a durable `provider_outcome_unknown` claim, so returning False cannot silently mark that uncertain outbound complete. All effects in these regressions are mocks; no provider was contacted.
