# Minimum missing bootstrap mechanism — design for scope review

Image preparation does not fix ingress. Inspected ICP1ea5f958 has no supported tenant forwarding-close action; its watchdog marker is only recovery suppression. Proposed scope is a small deployment-control addition to the existing ICP repository, not a new customer feature or forwarding service. No implementation or deployment is included yet.

## Small proposed change

- New app/tenant_ingress_gate.py: a Mermaid-only persistent open/closed generation record plus a dedicated admission lock, separate from the lifecycle lock. Default behavior remains open when no gate is installed. Never use inbox/AI controls or ownership deletion. File location must be explicitly bound to the existing ICP persistent data mount during release, not guessed from the default database path. State writes require same-directory atomic replacement/fsync and exclusive gate protection; malformed installed state fails closed for new Mermaid customer events.
- app/routes/connect.py: for a successfully resolved Mermaid message.received event, hold a shared admission lease through the existing generation-bound forwarding call and tenant acknowledgement. If closed, return503 with Retry-After5 before forwarding. This lease must be distinct from lifecycle locks and held in the existing worker-thread path, so tenant control callbacks stay available. Keep other tenants, noncustomer delivery/operator events, signature/ownership/generation validation and existing failure semantics unchanged. No duplicate marker or success ACK for newly rejected input.
- New host/mermaid_ingress_control.py: non-serving operator close/status/reopen utility, no public unauthenticated API. Close acquires the dedicated exclusive admission lock with a finite deadline, thereby waiting for admitted forwarding calls to finish, then writes the next closed generation durably. Status returns only generation/phase and fixed counters; reopen requires exact generation plus the separately verified runtime-ready condition supplied by the release action. A reference alone is not readiness proof. No forced expiry reopening. This utility is an operational mutation requiring the final release action's approval.
- tests/test_tenant_ingress_gate.py plus focused existing webhook-route tests: close races with forwarding; new events503/noforward; existing forward reaches ACK; control callbacks do not deadlock; other tenants and delivery events unchanged; stale generation/restart/crash/malformed state fail closed; finite lock timeout; no lost ACK or accidental provider/self-heal calls from inspection. All fixtures offline.

This introduces a third repository to the existing two-repository delivery. Review this exact scope before editing it. Deploying the control-plane change itself needs a bounded lifecycle plan: its forwarder does not ACK before receiving tenant response, but in-flight forwarding may yield a timeout and provider redelivery. Preserve downstream idempotency and all ownership bindings; no replay/delete of provider state. Source tests cannot establish the actual subscription's remaining retention.

## One coordinated bootstrap action after that mechanism is available

1. Verify the new ICP gate code is loaded for the existing router and its exact persistent gate location. Close Mermaid customer forwarding and record the returned generation only after its admitted forwarding calls finish. This is a forwarding barrier, not a claim that tenant background work finished.
2. Coordinate the named watchdog timer/service: stop future scheduling and wait for/stop its exact in-flight invocation under an approved action, then establish .maintenance. Inspect its completion/state and the exact Mermaid runtime identity before proceeding. A marker write by itself cannot fence a restart already past the marker check. Do not take the exclusive tenant lifecycle lock; do not run watchdog as a read-only check. Preserve/review Docker restart behavior as part of the same service action.
3. Prevent additional old scheduled/operator producers, allow a bounded graceful finish, then stop the old Mermaid runtime. Any timeout/unfinished claim remains uncertain, never “completed”. With all old writers stopped and new forwarding rejected, create a consistent backup and a fixed aggregate inventory of accepted/pending/paused/failed/superseded inbound and reservation/reminder/delivery/email/outbound claims. No customer data in public evidence. Require the operator to approve the exact remaining counts as retained no-replay/reconciliation work or stop and resolve them. Killing a worker does not establish a successful send.
4. Before starting a compatibility runtime with recovery enabled, apply a reviewed bootstrap retention journal/fence for those explicitly approved old claims, retaining original rows and their hashes. The current final Isluno activation quarantine exists, but it cannot protect a prior compatibility startup's old recovery loops. The compatibility step must therefore either start with all such producers demonstrably fenced or use an explicit reviewed direct-activation bootstrap that honors these retained dispositions. Do not assume the current coordinator can adopt unknown old claims automatically.

Step4 is a real additional implementation decision: the accepted coordinator deliberately refuses failed/unknown old work, and the existing final activation quarantine is later than compatibility startup. The smallest safe path is to inspect the aggregate first: if no unfinished old work exists and all producers are fenced, compatibility installation can proceed without a new disposition mechanism. If there is retained uncertain work, stop for a narrowly scoped bootstrap-journal/reconciliation design; do not loosen seal criteria, fabricate terminal statuses or hide it behind an evidence reference. The aggregate may therefore eliminate this extra work, but no empty state is assumed.

5. Install and verify the compatibility image/coordinator; with original work safely completed or explicitly fenced, run the accepted close/seal/current-generation activation and guarded reopen sequence. Reopen ICP admission only to the verified active tenant runtime; restore watchdog scheduling only after readiness. Provider retries then deliver to the same number/account, subject to actual configured eligibility.

## Why this is the minimum honest next step

An external new-connection firewall could theoretically reject tenant forwarding, but its actual container/network rules and established connections are unverified; introducing blind production firewall rules is not a supported shortcut. A shared ICP lifecycle lease already guards identity and ends at ACK, not all background work. The dedicated narrow admission gate addresses exactly the missing first half. The second half is either demonstrated empty old work or explicit retained no-replay dispositions before any recovery-capable restart. No broader control-plane rewrite or new product work is proposed.

Return scope approval/fixes before implementation. The final action still binds the exact image, current account/subscription/runtime, protected CAS, backup location, generation and window together; the known media/document paths are routine entries in that action, not separate user questions.
